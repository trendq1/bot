# IZIDVA AI Trader (PHP) — бот для фьючерсов Bybit с ИИ, Telegram Mini App и админ-панелью

Клиенты заходят в Telegram-бота, открывают мини-апп, бесплатно торгуют на демо-счёте, а по подписке
(Telegram Stars) подключают свой Bybit по вашей реферальной ссылке — бот торгует на их аккаунте.
Вы управляете всем из браузерной админ-панели.

> ⚠️ Торговля фьючерсами с плечом может привести к потере всех средств. Бот не гарантирует прибыль.
> Перед запуском для клиентов проконсультируйтесь с юристом: в ряде стран автоматическая торговля
> на счетах клиентов требует лицензии.

## Как устроено

| Часть | Как работает |
|---|---|
| Сайт: админ-панель, мини-апп, API, Telegram-бот (webhook), `migrate.php` | Обычные PHP-файлы. Работают сразу после загрузки — как любой PHP-сайт |
| Торговый движок `bin/daemon.php` | Постоянный процесс (служба systemd): рынок, сетки, сделки всех клиентов. **Не cron** — работает непрерывно, реагирует за секунды |
| ИИ-аналитик `bin/ai_worker.php` | Запускается движком автоматически отдельным процессом, чтобы запросы к Claude не тормозили торговлю |
| База MySQL / MariaDB | Клиенты, сделки, платежи, настройки, ключи (зашифрованы). Через неё сайт и движок обмениваются командами и состоянием |

## Требования

- PHP **8.1+** с расширениями `pdo_mysql`, `curl`, `openssl`, `mbstring` (в HestiaCP, ISPmanager, aaPanel есть по умолчанию).
- MySQL 5.7+ или MariaDB 10.3+.
- **HTTPS** — Telegram открывает мини-аппы и шлёт webhook только по HTTPS (в панели: Let's Encrypt).
- Для торгового движка — доступ к терминалу сервера **один раз** (VPS). Обычный виртуальный хостинг
  без SSH подойдёт только для сайта: торговля там работать не сможет, это ограничение хостинга, а не PHP.

## Установка

### 1. База данных
Панель → «Базы данных» → создать базу (MySQL, кодировка utf8mb4) и пользователя.
В HestiaCP к имени базы и пользователя добавляется префикс, например `admin_izidva` — запишите полные имена.

### 2. Загрузка файлов
Файловый менеджер → папка сайта (например `public_html`) → загрузить `izidva.zip` → **Распаковать**.
Получится папка `izidva` с `migrate.php`… внутри `public/`, а также `src/`, `vendor/`, `storage/`.

- **Apache** (HestiaCP с Apache, cPanel, большинство панелей): так и оставьте. Служебные папки закрыты
  файлами `.htaccess`, адреса: `https://ваш-домен/izidva/...`.
- **Только nginx**: `.htaccess` не работает — укажите корнем сайта папку `izidva/public`
  (в HestiaCP: Web → домен → Edit → Advanced → Custom document root).

### 3. Мастер установки
Откройте `https://ваш-домен/izidva/migrate.php`:
1. Код установки — в файле `izidva/storage/setup_code.php` (откройте файловым менеджером).
2. Данные базы из шага 1 → «Проверить подключение».
3. Логин и пароль администратора.
4. По желанию сразу: токен бота от @BotFather, ключ Anthropic (можно позже в админке).

«Установить» создаст таблицы, файл `storage/.env` с ключами шифрования и администратора,
подключит webhook Telegram-бота и кнопку меню.

> ⚠️ **Сразу скачайте себе копию `storage/.env`.** Это единственный файл с ключом шифрования — без него
> не восстановить сохранённые токены, ключ Anthropic и ключи Bybit клиентов. При повторной заливке архива
> **не распаковывайте новый zip поверх со сбросом папки** — если файловый менеджер вашего хостинга при
> «Заменить» сначала удаляет старую папку целиком, `.env` пропадёт вместе с ней. Если мастер установки
> при уже существующей базе вдруг предлагает создать нового администратора и предупреждает, что в базе
> уже есть данные, — значит `.env` только что потерялся; лучше остановиться и восстановить его из копии,
> чем продолжать (продолжение сгенерирует новый ключ, и все старые зашифрованные данные станут нечитаемыми).

### 4. Запуск торгового движка (один раз)
Мастер покажет команду — выполните её в терминале сервера:
```bash
sudo bash /home/admin/web/ваш-домен/public_html/izidva/bin/install-service.sh
```
Служба `izidva-engine` будет работать постоянно, перезапускаться при сбое и после перезагрузки сервера.
Больше терминал не нужен: всё остальное — в админ-панели.

### 5. Готово
- Админ-панель: `https://ваш-домен/izidva/admin/`
- Мини-апп: `https://ваш-домен/izidva/app/` (подставляется в настройки автоматически). Интерфейс двуязычный —
  украинский по умолчанию, русский переключается в мини-аппе на вкладке «Налаштування»/«Настройки».
  На вкладке «Сделки» — живой свечной график (Bybit, реальные цены) с отметками входов/выходов клиента
  и текущей позицией/сеткой; обновляется каждые ~4 секунды, пока открыта вкладка.
- В админке «Обзор» → блок «Торговый движок» показывает, работает ли он.

## Обновление версии
1. Загрузите новый архив и распакуйте поверх (папка `storage/` с `.env` сохраняется).
2. `sudo systemctl restart izidva-engine` — торговый демон сам применяет новые миграции при старте
   (`bin/daemon.php` → `Migrator::run()`), поэтому код, ожидающий новых колонок, больше не уходит в цикл
   перезапусков, если migrate.php забыли открыть. Вручную то же самое: `php public/migrate.php` или
   `https://ваш-домен/izidva/migrate.php` (войдя в админку).

### Отключение анализа и обнуление показателей

**⏸ Отключить анализ** (кнопка в шапке страниц «Обзор» и «ИИ и рынок», то же — настройка `analysis_enabled`): ИИ (Claude) не
вызывается ни для рынка, ни для разбора дня и графиков (расходы на ИИ прекращаются), демон не пересчитывает признаки и режим рынка,
режим принудительно `NO_TRADE`, все автостратегии запрещены. Уже открытые позиции и сетки сопровождаются как обычно (стоп, тейк,
закрытие); **ручная торговля и сигналы из Telegram работают**. Обратно — «▶ Включить анализ». Только очистить ключ Anthropic —
недостаточно: сделки продолжит открывать запасной алгоритм.

**🗑 Обнулить показатели** (Настройки и ключи → шапка; только роль admin; нужно ввести слово `ОБНУЛИТЬ`). Выполняет демон
(`Manager::resetStats`, единственный писатель сделок — гонок нет; команда старше 10 минут не выполняется), результат виден сразу.
- **Торговля** (по умолчанию включено): сделки и вся статистика PnL (в админке и в мини-аппе клиентов), обучение стратегий
  (`strategy_stats` и кэш), история баланса, сигналы, ручные ордера, состояние риска; демо-балансы возвращаются к стартовому
  (`paper_start_balance`), бумажные позиции отбрасываются, воркеры пересоздаются с нуля. Позиции на биржах Bybit (demo/live) не трогаются —
  движок подхватит их как «вне бота». Уроки и подстройки ИИ (`lessons`, `symbol_tuning`) остаются.
- **Финансы** (по умолчанию выключено): платежи за подписки и ручные записи доходов/расходов. Подписки клиентов не отменяются.
  Не сработает, пока есть неоплаченные реферальные начисления (они каскадно удаляются вместе с платежом — это долг перед людьми).
- **Расходы на ИИ (`ai_usage`) не затрагиваются никогда.** Операция необратима — при необходимости сначала сделайте дамп базы.

### Ордера и позиции (админка → 📈 Ордера и позиции)

Общая картина по всем клиентам или по одному (выпадающий список), обновляется каждые 5 секунд:
- **Сводка:** баланс, плавающий PnL в $ и % от баланса, реализовано сегодня / 7 / 30 дней ($ и % от баланса), Win Rate за 30 дней,
  сколько открыто позиций и ордеров.
- **Открытые позиции:** монета, сторона, стратегия (сетка / тренд / пробой / сигнал / вручную / «вне бота»), объём, вход, текущая цена,
  SL, TP, PnL в $, в % движения цены и в % от баланса. Кнопки **✎ SL/TP** (изменить стоп-лосс и тейк-профит; пустое поле — снять уровень)
  и **Закрыть** (закрытие по рынку; у сетки сворачивается вся сетка).
- **Открытые ордера:** лимитки входа, цели сигналов, ордера сетки; кнопка **Снять** (ордера сетки снимать нельзя — их ведёт сама сетка,
  закройте сетку целиком).
- **Доходность по клиентам:** плавающий результат, день %, реализованное за 7/30 дней, % за 30 дней и «с начала учёта» (от первого
  снимка баланса — пополнения и выводы не учитываются, поэтому это ориентир, а не точная доходность).
- **Последние закрытые сделки.**

Изменения выполняет торговый демон, а не веб-страница: админка ставит команду в `engine_commands` (`edit_stops`, `cancel_order`,
`manual_close`), демон исполняет её на бирже клиента и пишет результат в `engine_commands.result` (миграция 012) — админка ждёт его
до 12 секунд и показывает «Готово» или текст ошибки (например, «стоп-лосс должен быть ниже текущей цены»). Если бот клиента
остановлен, придёт «клиент не подключён». Позиции и ордера берутся с биржи клиента (у Bybit — `positions` с markPrice/stopLoss/takeProfit
и `order/realtime`), роль «трейдер» тоже видит эту вкладку.

### Ручная торговля и роль «трейдер»

- Роль **администратор** видит всю панель как обычно. Роль **трейдер** после входа видит только раздел
  «Ручная торговля» — остальные разделы и API для неё закрыты (403), даже если знать прямой URL.
- Для клиента можно выключить автотрейдинг («ручной режим») — сетка/тренд/ликвидации перестают открывать
  новые сделки, но уже открытые сетки и позиции движок по-прежнему сопровождает (тейк/стоп, закрытие).
  Включить автотрейдинг обратно можно тем же переключателем.
- Ручной ордер: **любая монета Bybit USDT-перпетуал** (не только те, что бот анализирует автостратегиями
  у этого клиента) — поле ввода с подсказками из списка бота, но принимает любой тикер вида `BTCUSDT`;
  рынок или лимит с ценой, необязательные тейк-профит/стоп-лосс, плечо. При первом ручном ордере по новой
  монете движок разово подгружает её спецификацию и цену с Bybit (`Market::ensureSymbol()`) — свечи и
  фичи для неё не строятся и AI-агент её не анализирует, она не участвует в автостратегиях клиента.
  Ордер встаёт в очередь и исполняется торговым движком (демоном) в течение нескольких секунд — так же,
  как автоматические сделки, на демо-счёте или на Bybit клиента. Статус (в очереди / исполнен / ошибка)
  обновляется в таблице ниже; лимитный ордер, который ещё не исполнился, можно отменить кнопкой «✕».
- **Открыть сразу всем клиентам** — галочка над формой ордера: тот же ордер (монета, сторона, тип, объём,
  тейк/стоп, плечо) ставится в очередь каждому незаблокированному клиенту отдельной строкой; кто сейчас не
  подключён или без биржи — просто получит ошибку по своей строке, остальным ордер всё равно исполнится.
- **Позиция, открытая или закрытая прямо на Bybit** (в приложении/на сайте биржи, мимо формы выше) — тоже
  попадает в статистику: на каждом такте Worker сверяет реальные открытые позиции клиента с тем, что сам
  отслеживает, и берёт под наблюдение любую «чужую» (`Worker::reconcileExternalPositions()`) — так же
  подхватываются позиции, которые бот открыл сам, но потерял из памяти после рестарта демона (это состояние
  не хранится в БД). Средняя цена входа берётся настоящая, с биржи; стоп и риск в R неизвестны, поэтому
  трейлинг/частичный тейк/принудительное закрытие по таймауту к таким позициям не применяются — бот только
  видит их закрытие и пишет сделку в статистику с реальным PnL.
- **Закрыть открытое** — карточка «Открыто у клиента сейчас» показывает все сетки, направленные позиции и
  неисполненные лимитные ордера выбранного клиента с кнопкой «✕ Закрыть»: сетка сворачивается, позиция
  закрывается по рынку, неисполненный лимит снимается с биржи — независимо от того, кто её открыл,
  автостратегия или трейдер.

## Оплата подписки: Telegram Stars + криптовалюта (NOWPayments)

Тарифы — аренда бота на **1 месяц ($15), 6 месяцев ($50), 1 год ($90)** по умолчанию. Цены в долларах
редактируются в админке → **Настройки и ключи** → группа «Тарифы» (поля «Аренда бота на 1 месяц/6 месяцев/1 год, $»);
цена в Telegram Stars для каждого тарифа считается автоматически по курсу «1 ⭐ в $» из той же группы.

Клиент в мини-аппе на вкладке «Настройки» видит переключатель способа оплаты (появляется только когда
NOWPayments включён) и жмёт тариф — дальше всё автоматически:
клиент выбрал тариф → его перекидывает на страницу оплаты NOWPayments → он платит любой криптовалютой →
NOWPayments присылает вебхук → подписка продлевается и клиент получает сообщение в Telegram. Ручных действий
администратора не требуется.

### Настройка (один раз)
1. Зарегистрируйтесь на [nowpayments.io](https://nowpayments.io), пройдите верификацию.
2. Личный кабинет → **API keys** → создайте ключ.
3. Личный кабинет → **Settings → IPN** → задайте **IPN Secret Key** (это отдельный секрет, не API-ключ).
4. В IPN-настройках укажите callback URL: `https://ваш-домен/izidva/nowpayments/webhook.php`
   (тот же адрес нужно передавать и в каждом инвойсе — бот делает это сам).
5. В админке → **Настройки и ключи** → группа **«NOWPayments (крипта)»**:
   - вставьте **API-ключ** и **IPN Secret Key**;
   - включите переключатель **«Оплата криптовалютой включена»**.

Готово — на вкладке подписки у клиентов появится выбор между ⭐ Stars и ₿ криптовалютой. Цена в долларах
берётся из тех же тарифов, что и Stars (курс — поле «Курс 1 ⭐ в $» в группе «Тарифы»).

### Как это устроено технически
- `MiniApi::pay()` при `method: "crypto"` создаёт инвойс через `POST /v1/invoice` NOWPayments
  (заголовок `x-api-key`) и сохраняет его в таблицу `crypto_invoices` со статусом `waiting`.
- Клиента через `tg.openLink()` (или обычную ссылку) отправляет на `invoice_url` — хостированную страницу
  оплаты NOWPayments, где он платит любой поддерживаемой монетой.
- `public/nowpayments/webhook.php` принимает IPN-вебхуки: проверяет подпись `x-nowpayments-sig`
  (HMAC-SHA512 от рекурсивно отсортированного по ключам JSON тела с IPN Secret Key), обновляет статус
  инвойса, а при статусе `finished` — записывает платёж и продлевает подписку клиенту (та же логика,
  что и для Stars, с защитой от повторного начисления по одному и тому же `payment_id`).
- В админке платежи через крипту помечены тегом «₿ крипта» и попадают в общую статистику доходов наравне
  со звёздами.

## Партнёрская программа

5-уровневая реферальная сеть: клиент приглашает по своей ссылке, и когда приглашённый (или его
приглашённые — до 5 уровней вглубь) **реально оплачивает подписку** (Stars или крипта), реферер получает
процент от суммы платежа. По умолчанию 20% / 5% / 3% / 2% / 1% по уровням — проценты и выключатель всей
программы редактируются в админке → **Настройки и ключи** → группа **«Партнёрка»**. Юзернейм бота для
реферальных ссылок задаётся там же, в группе **«Telegram»** (поле «Юзернейм бота»).

Клиент видит всё это на отдельной вкладке мини-аппа **«Команда»**: общий доход и доход за месяц, сколько
ожидает выплаты, свою реферальную ссылку с кнопкой копирования, разбивку дохода по 5 уровням (сколько
человек и сколько заработано на каждом), калькулятор-прикидку дохода по вводимым «сколько приглашу лично» /
«сколько пригласит каждый», и дерево команды — список приглашённых первого уровня с датой регистрации и
тем, сколько лично на каждом заработано.

**Важно: демо-счёт бесплатный и никогда не создаёт запись в `payments`, поэтому начисления партнёрам
физически невозможны с демо-торговли** — `Referral::creditForPayment()` вызывается только из мест, где
платёж уже реально создан (`Webhook::paid()` — Stars, `public/nowpayments/webhook.php` — крипта), больше
никаких путей начисления в коде нет.

### Как это устроено технически
- `users.referred_by` — кто пригласил (проставляется один раз, при первом `/start ref_<id>` от нового
  пользователя, см. `Webhook::handle()`); ссылка `https://t.me/<bot_username>?start=ref_<id>`.
- `referral_earnings` — леджер начислений: `beneficiary_id` (кому), `from_user_id` (чей платёж),
  `level` (1–5), `payment_id`, `pct`, `amount_usd`, `paid`.
- `Referral::creditForPayment($payerId, $paymentId, $usd)` поднимается по цепочке `referred_by` до 5
  уровней вверх и пишет по одной строке в `referral_earnings` на каждого реферера в цепочке.
- `MiniApi::team()` (`GET /team`) считает сводку: сумму по уровням, размер команды (`Referral::downlineCounts()`),
  косметический «ранг» по размеру команды (`Referral::rank()`) и список первого уровня для дерева.

## Торговая логика

- **Стратегии:** сетка (только в подтверждённом боковике), тренд на 1h (вход после отката к EMA20, стоп не
  ближе 1 ATR(1h), цель 2R с частичным тейком и трейлингом), отскок после каскада ликвидаций (по умолчанию
  выключен на платформе). Какие стратегии вообще допустимы, решает жёсткий режим рынка (`Regime`, см.
  «Risk Engine v3»); среди допустимых — `вес ИИ × множитель обучения × включена ли у клиента и на платформе`.
- **ИИ (Claude, официальный PHP SDK):** по каждой монете раз в N минут — режим рынка, веса стратегий,
  направление и шаг сетки, множитель риска. Раз в сутки — разбор сделок, уроки и подстройка параметров
  (±20% за день, в жёстких границах). ИИ не отправляет ордера и не может обойти лимиты риска.
  Без ключа работает запасной алгоритм.
- **Vision-разбор графика (опционально, `Settings::vision_enabled`):** отдельно от основного цикла анализа,
  раз в `vision_interval_min` на монету, ИИ смотрит на картинку свечного графика (рисуется на сервере через
  GD — `ChartRenderer`, без headless-браузера и без обращения к TradingView) и пишет короткую заметку —
  визуальные уровни, паттерны, общее впечатление (bullish/bearish/neutral). Это справочная информация для
  трейдера в мини-аппе (экран ІІ), она **не влияет на веса стратегий и не может открыть/закрыть сделку** —
  чтобы не подмешивать менее надёжное распознавание образов в автоматическое принятие решений. Выключено
  по умолчанию, так как vision-запросы дороже обычных текстовых.
- **Обучение:** по связке «монета × стратегия × режим» копится результат всех клиентов;
  убыточные стратегии получают до 0.4× капитала, прибыльные — до 1.6×.
- **Риск-профили:** консервативный / сбалансированный / агрессивный — риск на сделку 0.3/0.5/1%,
  плечо 5/15/25x, дневной лимит убытка 2/3/5%, ограничение убытка каждой сетки, пауза после серии убытков.
  На маленьком депозите сетка по BTC не строится — минимальный лот не помещается в лимит риска.
  Высокое плечо увеличивает объём позиций и риск ликвидации — реальный лимит плеча по каждой монете
  всё равно берётся у Bybit (`min(плечо профиля, максимум биржи для монеты)`).
- **Досрочный выход (`Worker::checkExit()`):** трендовая сделка закрывается по рынку, если часовая свеча
  закрылась за EMA50 (слом структуры) или режим развернулся против позиции / выброс волатильности, а позиция в
  минусе; в плюсе при развороте стоп переносится в безубыток (прибыльную сделку не режем по шуму). Отскок после
  ликвидаций — прежняя логика по режиму ИИ. Не раньше чем через минуту после входа. Сеток и ручных сделок
  трейдера это не касается — у сетки своя логика выхода, ручные позиции трейдер закрывает сам.
- **Диагностика убытков:** если сделка закрылась с результатом хуже −1.3R (обычный стоп ограничивает
  убыток примерно 1R), это пишется в `storage/logs/app.log` со входом/стопом/выходом/объёмом — повод
  разобрать конкретную сделку, а не совпадение.
- **Частичный тейк-профит:** на +1R по тренд- и ликвидационным сделкам половина объёма закрывается по рынку,
  остаток ведётся дальше трейлинг-стопом — снижает разброс результата между «всё по тейку» и «всё по стопу».
- **Трейлинг-стоп:** на +1R стоп переносится в безубыток (+0.06% сверх входа на комиссию), на +1.5R и дальше
  стоп следует за ценой на расстоянии 1R (было 0.8R/0.6R — слишком близко: прибыльные сделки выбивало шумом). Стоп двигается только в свою пользу, риск никогда не расширяется.
  На бирже это `POST /v5/position/trading-stop`, на бумажном счёте — обычная проверка цены против стопа.
- **Лимит по коррелирующим монетам:** вторую направленную (тренд/ликвидации) ставку не открываем, если по
  монете из той же группы уже есть открытая направленная позиция — группы: BTC/ETH/SOL/AVAX и XRP/ADA/DOGE/LTC.
  То же самое отдельно для сеток: вторую сетку в той же группе не открываем, пока активна первая — иначе общее
  движение группы (например, альты вместе с BTC) может выбить стопом сразу несколько сеток одновременно.
  Ручных сделок трейдера это ограничение не касается.
- **Пауза после стопа сетки:** если сетку выбило стопом (убыток), на этой монете новая сетка не откроется
  ближайшие 30 минут (`Worker::GRID_STOP_COOLDOWN_SEC`), даже если ИИ/алгоритм на следующем же такте снова
  сочтёт монету подходящей для сетки — не даём рынку тут же выбить вторую сетку подряд на том же движении.
- **Тихие часы и мёртвый рынок:** отскок после ликвидаций (5м) не открывается с 00:00 до 05:00 UTC и когда ATR
  меньше 0.07% цены. Для тренда на 1h это не нужно: слишком маленький стоп отсекает фильтр комиссии (`MAX_FEE_R`).
- **Дневной лимит числа сделок:** по консервативному/сбалансированному/агрессивному профилю не больше
  4/6/10 направленных (тренд/ликвидации) сделок в сутки на клиента — независимо от дневного лимита убытка
  в процентах. Сетка и ручные сделки трейдера в этот счётчик не входят, лимит сбрасывается по UTC-суткам.
- **Соотношение прибыли и убытка в сетке:** один цикл сетки (уровень открылся и закрылся) даёт маленькую
  прибыль ≈ шаг × объём. Но если цена пробивает все уровни и сетка закрывается по стопу, убыток — это сумма
  потерь по всем уже открытым уровням сразу, а не по одному. Во сколько раз максимальный убыток может
  превышать один цикл прибыли, зависит от числа уровней почти квадратично: `уровни × (уровни + 2) / 2`.
  Поэтому число уровней сетки уменьшено до 3/4/5 по профилю (было 6/8/10, затем 4/6/8) — для сбалансированного
  профиля один полный стоп теперь равен 12 циклам прибыли, а не 24 (изначально 40). Сумма стопа в $ по-прежнему
  задаётся `grid_max_loss_pct`; меняется то, сколько мелких плюсов он стирает. Цена — более узкий диапазон,
  который сетка держит без перестройки. Минимальный шаг сетки поднят с 0.2% до 0.3% (`Grid::MIN_STEP_PCT`):
  комиссия мейкера 2×0.02% съедала 20% прибыли каждого цикла, при 0.3% — 13%.
- **Выход из сетки, когда боковик закончился (`Worker::manageGrid()`):** сетка сразу перестаёт открывать новые
  уровни. Если режим ушёл против неё (сильный тренд против стороны сетки, пробой, выброс волатильности) и на
  инвентаре плавающий убыток — закрывается по рынку сразу (`kind=reversal`). Если боковик просто закончился и не
  вернулся за 30 минут (`GRID_REGIME_EXIT_SEC`) — убыточный инвентарь тоже закрывается (`kind=regime_exit`):
  держать его «пока сигнал формально не отменён» — ровно то окно, где случались крупные стопы. В плюсе —
  открытые уровни мягко доводятся до своих тейков.
- **Точный PnL стопа сетки на реальной бирже:** маркет-ордер, которым сетка закрывается по стопу, исполняется
  не мгновенно, и цена до его отправки может не совпасть с фактической ценой исполнения при проскальзывании
  (стопы срабатывают как раз на резких движениях, где слиппедж самый большой). На реальной бирже (live/demo)
  сетка помечает стоп как `pendingStop` и ждёт факт исполнения с Bybit (`GET /v5/position/closed-pnl`,
  `Worker::checkGridStops()`) — так же, как уже считается PnL направленных сделок — вместо того чтобы
  занижать/завышать убыток оценкой по последней увиденной цене. На бумажном счету цена известна точно и сразу,
  это ничего не меняет.
- **Точный PnL закрытия направленных сделок:** когда позиция исчезает с биржи, Bybit отражает её в
  `/v5/position/closed-pnl` не мгновенно. Раньше, если история ещё была пустой, сделка записывалась с PnL 0 и
  выходом = входу (в статистике — строки вида `84310.1 → 84310.1`, `-0.00 $`, `R 0`), и реальный результат
  терялся — в том числе для обучения. Теперь `Worker::checkDirectional()` ждёт до минуты
  (`CLOSED_PNL_WAIT_MS`) и только потом оценивает PnL по последней цене (с комиссией тейкера).
- **Уведомления в Telegram:** бот больше не шлёт клиенту сообщения о входах/выходах по стратегии и о паузе
  после серии убытков — эти события видно в мини-аппе (открытые сделки, история, статус). Сообщения о
  действиях трейдера вручную (открыл/закрыл/отменил) по-прежнему приходят, так как это прямое действие
  человека с деньгами клиента, а не рутинный сигнал стратегии.

## Risk Engine v2

Главный критерий здесь — не Win Rate, а **Profit Factor, Expectancy, просадка и хвостовые (tail) убытки**:
много мелких выигрышей и не может, и не должно компенсировать редкий убыток, который их уничтожает — система
защищается от этого на нескольких независимых уровнях, а не одним параметром.

- **Бюджет на сделку (клиентская настройка, мини-апп → Настройки):** `budget_mult` — множитель 50–150% поверх
  риска/капитала, который профиль выделяет на сделку (`Worker::BUDGET_MULT_MIN/MAX`, клэмпится и на бэкенде
  независимо от того, что пришло от клиента). Масштабирует ОДНОВРЕМЕННО и размер позиции, и её риск-бюджет
  (`maxLoss` сетки / `riskUsd` направленной сделки) — так соотношение убыток/прибыль внутри одной сделки не
  меняется, просто вся сделка пропорционально больше или меньше. Диапазон специально скромный (не произвольный
  процент): Grid Risk Protection и Portfolio Risk Engine всё равно ограничивают сумму сверху, но сам диапазон
  подобран так, чтобы не потребовалось об это думать — 150% от базового риска профиля уже ощутимо, но не
  разрушительно даже на агрессивном профиле.
- **Portfolio Risk Engine (`max_floating_loss_pct`):** новый лимит на СУММАРНЫЙ нереализованный (floating)
  результат по всем открытым сеткам и направленным сделкам клиента разом (`Worker::floatingPortfolioPnl()`,
  `RiskGuard::allowed()`). В отличие от `daily_loss_pct` (это уже зафиксированный убыток), floating-лимит
  срабатывает раньше — когда несколько позиций одновременно проседают на одном движении рынка, но ещё не
  закрылись по своим стопам. Блокирует только НОВЫЕ входы, существующие позиции не трогает.
- **Grid Risk Protection (`max_total_grid_risk_pct`):** явный лимит на сумму `max_loss` всех одновременно
  открытых сеток клиента (`Worker::startGrid()`). Раньше суммарный риск по сеткам был неявным произведением
  `grid_max_loss_pct × max_grids`; теперь это отдельная, видимая настройка профиля, дальше от которой можно
  безопасно отступить, не трогая другие параметры.
- **Grid Safety — жёсткий код-блок, а не совет ИИ:** `Indicators::isExtremeVolatility()` (ATR в разы выше своей
  медианы) и `Indicators::isBreakout()` (одновременно расширение ATR + всплеск объёма + резкий наклон EMA20)
  запрещают открытие НОВОЙ сетки на уровне кода — это проверяется в `Worker::manageSymbol()` независимо от
  того, что скажут веса ИИ/алгоритма. AI это обойти не может: он не видит и не трогает эту проверку.
- **Adaptive Risk (`RiskGuard::adaptiveMult()`):** чем глубже просадка от пика equity клиента, тем меньше
  множитель размера новых позиций (от 1.0 до пола 0.4) — применяется поверх `risk_mult` от ИИ и в сетке, и в
  направленных сделках. Восстанавливается сам по мере роста equity обратно к пику, без ручного сброса.
- **Cooldown после крупного убытка:** у сетки такая пауза была и раньше (`GRID_STOP_COOLDOWN_SEC`, 30 минут на
  монете после стопа); теперь то же самое для направленных сделок — после результата хуже `BIG_LOSS_R_THRESHOLD`
  (-1.5R) новая ставка (тренд/ликвидации) на этой монете не откроется `BIG_LOSS_COOLDOWN_SEC` (30 минут).
- **Grid Session PnL:** у каждой сетки есть `session_id` (`Grid::$tag`) — по нему в таблице `trades` можно
  агрегировать всю «жизнь» одной сетки (все циклы + финальный выход) как одну операцию: сколько всего
  заработано/потеряно, сколько было циклов, чем закончилось (`kind`: `cycle`/`stop`/`reversal`). Раньше PnL
  сетки был виден только по отдельным сделкам, без возможности увидеть сессию целиком одним запросом.
- **Learner — не только Win Rate:** `strategy_stats` и `Learner::statsFor()` теперь считают Profit Factor,
  Expectancy (в R и в $), средний выигрыш/проигрыш в R и худший R (tail loss) по каждой связке
  монета×стратегия×режим. Это же передаётся в `learning_stats` ИИ при анализе (`AIAnalyst::analyze()`) — в
  системный промпт добавлено прямое указание ориентироваться на `profit_factor`/`expectancy_r`, а не на
  winrate: высокий винрейт с `profit_factor < 1` — это убыточная стратегия, даже если почти все сделки в плюсе.
  Вес стратегии (`Learner::mult()`) считается по худшему из двух: EWMA результата в R (помнит ~10 последних
  сделок) и полного Expectancy по всей выборке. Только по EWMA у сетки вес почти всегда был выше 1: между редкими
  крупными стопами идут серии мелких плюсов, и EWMA успевает «забыть» стоп, хотя в сумме стратегия в минусе.
- **AI не может превысить жёсткие лимиты:** ИИ по-прежнему управляет только `AIAnalyst::TUNABLE`
  (`grid_step_atr`, `trend_rr`, `liq_threshold_mult`) и весами стратегий — `grid_levels`, `grid_max_loss_pct`,
  `max_total_grid_risk_pct`, `max_floating_loss_pct`, плечо, размер позиции заданы в `Risk::PROFILES` и ИИ
  до них не достаёт вообще. Все перечисленные выше защитные механизмы (Grid Safety, Adaptive Risk, Portfolio
  Risk Engine) — код, который ИИ не видит и не может обойти весами или уверенным тоном в summary.
- **Trade Analytics (админка → Обзор, `TradeStats`):** Net PnL, Expectancy в $ и в R, Profit Factor, средний
  плюс/минус и их отношение, крупнейший плюс/убыток, максимальная просадка по кривой реализованного PnL,
  Recovery Factor, Sortino (от 30 сделок), доля всех убытков от 1% / 5% / 10% крупнейших убыточных сделок, сессии
  сетки (PF сессий, худшая сессия, «1 стоп = N циклов прибыли») и таблицы по стратегиям, режимам рынка, монетам и
  часам UTC (`GET /admin/api/index.php/analytics`). Тот же `TradeStats` считает отчёт бэктеста.
- **Backtest / walk-forward / Monte Carlo (`bin/backtest.php`):** прогоняет ТЕ ЖЕ классы, что и прод
  (`Worker`/`Grid`/`Setups`/`Regime`/`Brain`/`PaperExchange`), по историческим 5м-свечам Bybit или CSV:
  время такта — время свечи (без смешивания истории с текущими часами), цена внутри свечи проходит через
  high/low (стопы и исполнения внутри свечи не теряются), часовые свечи собираются из 5м без заглядывания
  вперёд, комиссии/проскальзывание/гэпы — как в `PaperExchange`, funding — постоянная ставка. ИИ не вызывается
  (`AIAnalyst::ruleInsight`), в боевую БД и лог ничего не пишется. Параметры фиксированы, подгонки нет — каждый
  отрезок walk-forward для них out-of-sample; Monte Carlo перемешивает последовательность сделок и показывает
  перцентили итога и просадки и вероятность минуса. Отскок после ликвидаций не тестируется (нет истории ликвидаций).
  ```
  php bin/backtest.php ETHUSDT --days=180 --profile=balanced --folds=6 --mc=1000
  php bin/backtest.php ETHUSDT --csv=eth_5m.csv --json=report.json   # CSV: ts_ms,open,high,low,close,volume
  ```
  Вердикт печатается только по фактам: меньше 30 сделок — «данных недостаточно», PF < 1 — «не включать», плюс
  только на части отрезков — «нестабильно». Даже при PF ≥ 1 на всех отрезках это не обещание прибыли, а
  допуск к следующему шагу — demo/paper минимум 2–4 недели.
- **Funding в PnL:** раньше funding нигде не вычитался — ни биржа не включает его в `closedPnl()`, ни бот его
  не считал. Теперь `Worker::fundingEstimate()` грубо оценивает funding-costs по времени удержания
  (notional × текущая ставка × часы/8) и вычитает из PnL — для направленных сделок при каждом закрытии, для
  сетки только на финальном стопе сессии (не на каждом мелком цикле — те держатся слишком коротко, чтобы
  funding был заметен). Это оценка по последней известной ставке, не точная сумма из истории транзакций биржи
  за весь период удержания — но давать ноль, как раньше, было хуже, чем разумное приближение.

## Risk Engine v3 — торговать только там, где есть преимущество

Аудит реальных сделок (159 сделок 26–28.09: Net −8.55$, PF 0.73 при Win Rate 81%) показал три источника
убытка, и каждый закрыт в коде, а не подбором параметров:

1. **Тренд на 5м был отрицательным по устройству:** стоп 0.5–1 ATR(5м) ≈ 0.1–0.3% цены при комиссии тейкера
   0.11% за вход+выход — комиссия съедала 50–120% R (плюс ≈ +0.9R, минус ≈ −1.6R, нужен был Win Rate ~63%,
   был 38%). Теперь тренд — на 1h: стоп не ближе 1 ATR(1h), цель 2R, и **фильтр комиссии**: сделка не
   открывается, если комиссия за вход+выход больше 15% риска (`Worker::MAX_FEE_R`, `Setups::feeR()`).
   Объём считается от риска до стопа ВКЛЮЧАЯ комиссии; вес стратегии и ИИ могут только уменьшить риск (≤ 1.0).
2. **Сетка усредняла в лонг на падающем рынке:** 130 из 135 сделок сетки — покупки («боковик» = «тренд не найден»,
   а сторона — «ниже VWAP → лонг»). В разбивке по режимам в плюсе был только боковик (PF 1.36), остальное — в минусе.
   Теперь сетка открывается только в **подтверждённом RANGE** и сторона — по положению цены в суточном диапазоне
   (нижняя треть — лонг, верхняя — шорт, середина — не ставим).
3. **Рестарты демона:** сетка и её стоп жили только в памяти — при перезапуске все сетки закрывались по рынку
   (27.09 14:46:42 — −10.5$ за одну секунду, 60% всех убытков сетки), а при падении процесса позиция оставалась
   вообще без стопа. Теперь стоп сетки — **настоящий стоп-лосс позиции на Bybit** (`Grid::ensureExchangeStop()`),
   при остановке на реальной бирже сетка «отпускается» (`Grid::detach()`: сняты только входы, позиция остаётся со
   стопом и тейками), а состояние риска сохраняется в `worker_state.risk_state` (миграция 010).

**Цепочка решения (`Worker::manageSymbol()`):** режим рынка → качество сетапа → есть ли edge → риск портфеля →
вход → размер → выход → статистика. По умолчанию — **NO_TRADE**.

- **Режим рынка (`Regime::classify()`, по 1h + подтверждение 4h + всплески 5м):** `strong_up` / `strong_down`
  (ADX(1h) ≥ 25, EMA20/50/200 выстроены, наклон EMA50, 4h не против), `range` (ADX(1h) < 20 и ADX(5м) < 25,
  плоская EMA50, суточный диапазон ≥ 3 ATR), `breakout`, `high_volatility`, `weak_trend` (всё неоднозначное),
  `no_trade` (нет истории). Разрешения (`Regime::allows()`): тренд — только сильный тренд, сетка — только
  RANGE, отскок — RANGE/высокая волатильность; в `weak_trend`/`breakout`/`no_trade` новых сделок нет.
  Это код, ИИ его не видит и не может переопределить весами — в промпт ИИ режим передаётся как `hard_regime`.
- **Risk Engine (параметры в `Risk::PROFILES`, консерв./сбаланс./агрес.):** риск на сделку 0.3/0.5/1%;
  `max_portfolio_risk_pct` 2/4/8% (сумма риска до стопов всех позиций и сеток); `max_correlated_risk_pct`
  1.5/2.5/4% (внутри группы коррелирующих монет); `max_exposure_mult` 2/3/5× (номинал позиций к депозиту);
  `grid_max_loss_pct` 1/1.5/2.5%; `max_total_grid_risk_pct` 2/3/6%; `max_floating_loss_pct` 3/4/8%;
  `max_strategy_dd_pct` 2/3/5% — просадка стратегии от её пика ставит её на паузу на сутки; дневной лимит
  убытка 2/3/5%; пауза после серии убытков; кулдаун после крупного убытка; Adaptive Risk по просадке.
  У ручных/внешних позиций с неизвестным стопом риск считается как 2% номинала.
- **Аварийная остановка (админка → Настройки → «АВАРИЙНАЯ ОСТАНОВКА»):** все сетки и позиции всех клиентов
  закрываются по рынку один раз, новые сделки не открываются, пока выключатель включён.
- **Выключатели стратегий на платформе:** `strategy_grid_enabled` / `strategy_trend_enabled` /
  `strategy_liquidation_enabled` — поверх настроек клиентов (отскок после ликвидаций по умолчанию выключен:
  на истории его проверить нельзя). Выключайте стратегию, если её бэктест на реальных данных отрицательный.
- **Демо-биржа не приукрашивает:** лимитка исполняется только если цена прошла сквозь уровень (не касание),
  стоп через гэп — по худшей цене, рыночные исполнения — с проскальзыванием 0.02%.

**Пробой канала 4h (`strategy=breakout`, по умолчанию ВЫКЛЮЧЕН на платформе):** трендследование с классическими,
не подобранными под историю параметрами (система «черепах» / Chandelier Exit): закрытие 4h-свечи выше максимума 20
предыдущих и выше EMA50(4h) — лонг, зеркально — шорт (`Setups::breakout()`, только закрытые 4h-свечи —
`Indicators::closedBars()`); не догоняем, если цена ушла от уровня дальше 1 ATR; стоп 2 ATR(4h); тейка нет —
стоп следует за лучшей ценой на 3 ATR (`Worker::applyChandelier()`), без частичного тейка на +1R; максимум 30 дней.
Профиль ожидаемо «мало прибыльных сделок, но крупных». Проверка бэктеста на случайном блуждании (где преимущества
нет по определению) даёт PF 0.8–0.9 — утечки будущего в бэктесте нет. Включать только если на РЕАЛЬНОЙ истории
выполнен критерий, заданный до прогона (печатается бэктестом): PF ≥ 1.2 за весь период и минимум в 4 из 6 отрезков,
не меньше 30 сделок — на большинстве проверенных монет:
```
php bin/backtest.php BTCUSDT --days=730 --folds=6 --strategies=breakout; sleep 30
php bin/backtest.php ETHUSDT --days=730 --folds=6 --strategies=breakout; sleep 30
php bin/backtest.php SOLUSDT --days=730 --folds=6 --strategies=breakout; sleep 30
php bin/backtest.php XRPUSDT --days=730 --folds=6 --strategies=breakout
```

**Как проверять перед реальными деньгами:** `bin/backtest.php` по каждой монете на 90–180 днях → монеты/стратегии
с PF < 1 или нестабильные по отрезкам выключить → demo 2–4 недели, смотреть Trade Analytics (PF, Expectancy,
хвост убытков, сессии сетки) → только потом реальный счёт. Слово «прибыльная» по одному бэктесту не применяем.

## Сигналы из Telegram-канала

Бот может копировать сделки из канала со стабильным форматом сообщений (`App\SignalParser`, строгий шаблон без ИИ —
цифры не «додумываются»): `#МОНЕТА/USDT`, ЛОНГ/ШОРТ, «в диапазоне $a - $b», «Закрыть по $…» (цели), «СТОП ЛОСС: $…».

**Настройка (админка → Настройки → группа «Сигналы»):**
1. Включите `Сигналы из Telegram`.
2. `Разрешённые источники` — ваш Telegram ID (пересылаете сигналы боту в личку) и/или ID канала (`-100…`, бот должен
   быть админом канала; после этого пересохраните токен бота, чтобы webhook начал получать посты каналов —
   `channel_post`). Сообщения от всех остальных игнорируются.
3. По умолчанию сигналы исполняются **только на демо-счетах** клиентов; реальные — включаются отдельной галочкой
   `Исполнять и на РЕАЛЬНЫХ счетах`. Допуск ухода цены от зоны входа — `0.3%`.

**Что происходит:** сообщение → разбор → проверки (`SignalParser::validate`: стоп с нужной стороны, цели по порядку в сторону
прибыли, диапазон входа ≤ 3%, стоп ≤ 15% от входа) → дедупликация (та же монета и сторона, вход в пределах 1.5% за 12 часов
— дубль) → в чат приходит подтверждение → демон для каждого клиента (`Worker::signalOrder`):
- цена в зоне входа или лучше — вход по рынку; чуть вне зоны (в допуске) — лимит на границе зоны (снимается через 4 часа);
  дальше допуска или первая цель уже взята — сигнал пропускается, бот не догоняет;
- **размер позиции — от риска клиента и расстояния до стопа с учётом комиссий** (как у остальных стратегий), а не «плечо X25»
  из канала; лимиты портфеля, корреляции и экспозиции работают как обычно;
- стоп-лосс сигнала ставится на биржу сразу; цели — лестница reduce-only лимиток равными долями (`applySignalLadder`);
  после первой сработавшей цели стоп переносится в безубыток; при закрытии остатки лестницы снимаются;
- сделки пишутся как стратегия `signal` — в Trade Analytics виден отдельный PF/Expectancy по каналу; просадка сигналов
  сверх `max_strategy_dd_pct` ставит приём новых сигналов на паузу на сутки.

Итог по каждому сигналу и клиенту — в таблицах `signals` / `signal_orders` и в карточке «Сигналы из Telegram» на странице
«Ручная торговля». **Прежде чем включать реальные счета, 2–4 недели гоняйте канал на демо** и смотрите PF/Expectancy по
стратегии «Сигнал»: у сигнальных каналов редко есть проверяемая статистика.

## Безопасность
- Ключи Bybit клиентов и ваши ключи шифруются (AES-256-GCM, ключ в `storage/.env`).
- Ключ Bybit с правом вывода отклоняется; реальный счёт — только для ваших рефералов.
- Мини-апп принимает только запросы с подписью Telegram; webhook — только с секретом.
- Админка: пароли bcrypt, подписанная cookie, защита от перебора и CSRF.
- **Храните копию `storage/.env` отдельно** — без него зашифрованные ключи не восстановить.
